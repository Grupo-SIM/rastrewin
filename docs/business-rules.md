# Business Rules

Source of truth for product and domain rules. Keep engineering workflow and agent rules in `AGENTS.md`.

## Products

- **Rastrewin raffles** (`frontend`, `backend`): landing, sign-up and checkout; `/dashboard` with the user's raffles; `/admin` where the admin defines each raffle's winner. A winner is shown to the user only when the raffle time is over **and** the admin has set one; otherwise the UI shows "Apurando resultado...". Raffle data is mocked.
- **Tracking** (`track`): server-side tracking that captures visitors and events, sends them to Meta Conversions API and GA4, receives sales relayed by the rastrewin backend and shows everything in a panel. Its rules (RLS, secrets, retention, geolocation attribution) live in [`track/AGENTS.md`](../track/AGENTS.md) and [`track/SECURITY.md`](../track/SECURITY.md).
- **VSL page** (`vsl`): static video sales letter page that precedes https://rastrewin.com, served at vsl.rastrewin.com. No backend and no database; it loads the track script (`t.js`) to record the visitor and the ad origin. Rules live in [`vsl/AGENTS.md`](../vsl/AGENTS.md).

## Sales and attribution

- Funnel: ad → VSL → rastrewin.com sign-up form → SimIntPay checkout (a payment link per plan).
- Both sites load `https://track.rastrewin.com/t.js`. Visits from the Meta and Google networks (ad review and link-preview robots that run the page) are ignored by the track: they are not visitors and nothing is sent to Meta/GA4 for them. The visitor id cookie (`_trck`) is set on `.rastrewin.com`, so the VSL and rastrewin.com share the visitor.
- On submit, the form identifies the lead and sends the visitor's tracking (`src` = `trck_user_id`, UTMs, `fbc`, `fbp`) with the sign-up; the backend stores it. Once the backend saves the sign-up, the form sends `CompleteRegistration` with the plan (`content_ids` = plan id, value in BRL); in GA4 that event keeps the name `generate_lead`. It is sent only for the first sign-up of an e-mail (the backend answers `firstSignup: true`); a re-submit (fixing data, changing plan, coming back from the checkout) does not send it again, but still sends `InitiateCheckout`. It then opens the checkout with the same tracking in the URL query, which SimIntPay returns in the sale event, so the sale is tied to the visit even when the buyer types a different e-mail at checkout. `InitiateCheckout` fires only when that navigation is dispatched to a valid `https` checkout link (new tab, or this tab when the popup is blocked); an invalid link shows an error and sends no `InitiateCheckout`. The page cannot see SimIntPay's page load, so "checkout opened" means "navigation dispatched". The t.js script on rastrewin.com carries `data-no-auto`, so clicks on checkout links (the customer area's "Renovar assinatura") never fire an automatic `InitiateCheckout`; the links are still decorated with `src`, UTMs, `fbc` and `fbp`. The e-mail typed in the hero form is identified on submit (`trck('identify', { email })`), so the following events already carry it (after consent only, like every t.js command).
- **Meta event map (landing page, `frontend/lib/funnel.ts`):** `PageView` (t.js, every page load); `SectionView` (`section`: `como_funciona`, `automatico`, `probabilidades`, `resultado_ao_vivo`, `planos`, `formulario`, `faq`; the hero is left out because it is always visible; once per section per page view, when 30% of it, or 30% of the screen, is visible); `ScrollDepth` (`percent`: 25, 50, 75, 90; once per mark per page view, measured at the bottom of the screen); `CTAClick` (`button` + `section`: `comecar_topo`/`cabecalho`, `comecar_hero`/`hero`, `comece_agora`/`resultado_ao_vivo`, `continuar_pagamento`/`planos`); `ViewContent` (standard event, with the same trigger as `SectionView planos`, once per page view: `content_ids` = `basico`, `pro`, `vip`, `content_type: product`, `content_name: Planos`); `PlanSelect` (`plan`, only when the choice changes); `RegistrationStart` (first change to a field of the full form, once per attempt; a failed submit starts a new attempt); `CompleteRegistration`; `InitiateCheckout`; `AddPaymentInfo` (server only, webhook: SimIntPay `pix_generated` or `card_declined`, once per order, see below); `Purchase` (server only, webhook). Custom events, `ViewContent` and `AddPaymentInfo` go to Meta only (`ga4: false`). Every browser event goes through t.js, so the consent rule is the same for Pixel and Conversions API, and both channels carry the same `event_name` and `event_id`. `Lead` is no longer sent to Meta (no custom conversion, audience or ad set used it on 2026-11-14).
- **Meta event map (VSL, `vsl/src/lib/meta-events.ts`):** `PageView` (t.js); `VSLStart` (first Vimeo `play` per page load; `video_id`); `VSLProgress` (`percent`: 25, 50, 75, 95 of the video's duration, counted by seconds really watched, so skips and replays don't count; once per mark per page load; `video_id`; nothing while the duration is unknown); `VSLCTAUnlock` (the button unlocks, with `reason`: `watched` = the unlock seconds were really watched, `ended` = the video ended first, `error` = the player failed after the tap; a button remembered from an earlier visit is not a new unlock and sends nothing); `CTAClick` (`button: quero_conhecer`, `section: vsl`, click or middle click). All carry `page_type: "vsl"` and go to Meta only (`ga4: false`), through t.js like the landing events. The detailed video progress stays in the panel's Vídeos tab; Meta gets only the `VSLProgress` marks.
- **Ad origin from the VSL to the landing (`vsl/src/lib/forward-origin.ts`):** the VSL button link carries the visit's `utm_*` and `fbclid` (no other parameter) to rastrewin.com, in the URL only; the VSL stores nothing. The landing's t.js reads them only after the banner is accepted, so a visitor who left the banner unanswered on the VSL and accepts on the landing keeps the ad origin (UTMs in the visitor, `_fbc` from the `fbclid`, and both in the sign-up and checkout tracking). A refusal (`_trck_consent` with `m: false`, any text version) sends the plain link.
- SimIntPay sends each sale event to the backend, which confirms the purchase and relays the event to the track. The track ties the sale to the visit through `src`, falling back to e-mail or phone. Details: [SimIntPay integration](development/simintpay.md).
- Only the first purchase goes to Meta and GA4 as `Purchase`. Repurchases and renewals (the buyer already had a paid order) are not sent.
- **Annual subscription:** plans are annual subscription offers in SimIntPay (Pix paid each cycle, card charged automatically). Each paid cycle extends access by one year from the current expiry (or from the payment, if already expired), once per order; it is a renewal, so it never goes to Meta/GA4 as `Purchase` nor generates `AddPaymentInfo`.
- **`AddPaymentInfo` (Meta only, server side):** when SimIntPay reports `pix_generated` or `card_declined`, or approves an order that has had none yet (`purchase_approved`), the track sends `AddPaymentInfo` through the Conversions API with the same match data, value and items as `Purchase`, plus `payment_method` (`pix` or `credit_card`, from the method SimIntPay reports; omitted for any other method, so audiences can split Pix from card), once per order (`event_id` = `addpaymentinfo_<order>`, also recorded in `events_log`, so it shows in Eventos and in the visitor journey). It is sent only when the sale is linked to a visitor who accepted the banner, the order is not a renewal (the backend flags `renewal` on `pix_generated` and `card_declined` too), the notice is less than 7 days old and the order is still pending or declined (for `pix_generated`/`card_declined`) or active (for the approval). SimIntPay has no "card entered" notice, so a card approved at the first try only sends `purchase_approved`: the approval then sends `AddPaymentInfo` first, timed 1 s before the sale, and `Purchase` right after. The same covers a Pix whose `pix_generated` arrives after the approval (that late notice then sends nothing). `Purchase` still goes out only on approval. One attempt, like the site events; a failure stays in the event's Meta response.
- **Product id across the funnel:** the backend relays the sign-up plan (`plan`: `basico`, `pro` or `vip`; the newly chosen one for an active customer) with `purchase_approved`, `pix_generated` and `card_declined`. The track uses it as the id of the sale's main item, so `Purchase`, `AddPaymentInfo` and the GA4 `purchase` carry the same `content_ids`/`item_id` as `InitiateCheckout`. Without it (a buyer who used another e-mail at checkout), the SimIntPay offer id stays.
- **Renewals in the panel (one rule for every tab):** revenue counts everything, because it is money that came in; acquisition numbers count only new sales. So Receita (Visão geral and Faturamento) and Faturamento's Compras/Ticket include renewals, and the panel shows how much came from them (Visão geral hint, Faturamento "Renovações" card). Visão geral's Compras, Conversão, funnel and ROAS, plus Geo, Campanhas, Páginas and Vídeos, count only new sales.
- **Affiliates:** SimIntPay owns the affiliate registry and pays the commission; Rastrewin only captures the affiliate code (`aff`, format `^[A-Za-z0-9_-]{3,40}$`, anything else is ignored). The code arrives as `?aff=CODE` on the VSL or rastrewin.com and is kept in the necessary cookie `_trck_aff` (last click, 30 days, written by `t.js`). The frontend reads that cookie directly (`readTracking` in `frontend/lib/track.ts`), with no dependence on `t.js` loading or on consent, and sends `aff` with the sign-up tracking (stored in `User.tracking`) and in the checkout URL query. The relay sends it with the rest of the tracking (the checkout's wins; the sign-up copy fills in). The sale is attributed to the affiliate by SimIntPay, which decides who gets paid and how much and reports it in the sale event; `tracking.aff` is only a fallback key. A refund or chargeback reverses the commission on SimIntPay's side. Without the cookie nothing changes.
- Refund and chargeback revoke the plan of the order that was refunded. The track marks the sale refunded and sends a GA4 `refund`; Meta receives nothing for refunds.
- Once a sale is approved, its value, product, UTMs and visitor link are fixed. Later events for the same order (refund requested, refund, chargeback) change only the status and the refund date, so the amount they carry never rewrites revenue and the tracking the backend attaches to them never moves the sale to another campaign. Only a new approval of the same order can update those fields. Each raw event stays in `webhook_events`.
- Every track event carries the same UTMs as `identify`, so an event that reaches the server before `identify` (the first PageView) still records its origin.

## Privacy (LGPD)

Owner-facing guide (what was built and what to customize): [track/docs/lgpd.md](../track/docs/lgpd.md).

- **Consent first:** `t.js` shows a consent banner (categories: necessary and "marketing and measurement"; reject is as prominent as accept). Nothing of marketing or measurement runs before the visitor accepts: no visitor id, no UTMs stored, no `_fbp`/`_fbc`, no Pixel, no GA4, no events, no video progress. Commands called before acceptance are dropped, not queued.
- The choice is stored in the `_trck_consent` cookie (1 year) and recorded in the track (`consent_records`: random choice id, action, text version, site and page path; no IP, no browser). Changing the text version in the panel asks everybody again. The footer of each site has "Preferências de cookies"; declining after accepting revokes: the browser's marketing cookies are deleted and the visitor's Meta/Google ids are erased in the track.
- **Data subject rights (access and erasure):** anyone can ask at `rastrewin.com/privacidade/solicitacao` with an e-mail (phone optional). Nothing happens until they confirm through the single-use link sent to that e-mail (30 min); the reply never reveals whether the e-mail has an account. The phone counts only when it is the phone of that e-mail's account. Access shows and downloads (JSON) the account, browsing, purchases and cookie choices. Erasure deletes the visitor, events and video plays, anonymizes purchases (order, value, date, status and product stay, for tax records), anonymizes the account (closing access, even of a paid plan) and lists the visitor's GA4 client ids in the track panel for manual deletion in GA4. Meta cannot delete events it already received. For 30 days after an erasure, a sale for the same e-mail/phone is stored without personal data.
- **Privacy policy** (`rastrewin.com/privacidade`, `frontend/app/privacidade/page.tsx`) describes exactly this behavior: consent as the legal basis for marketing and measurement, what goes to Meta (hashed contact data) and Google (no contact data), the cookie table, the retention table and the rights (form, limits). Its version must match the banner's text version in the track panel; changing what is collected or shared means bumping both.
- **Exception: necessary cookie `_trck_aff`.** Before any choice, and surviving a rejection or revocation, `t.js` may write `_trck_aff` on `.rastrewin.com` (30 days, `Secure`, `SameSite=Lax`) holding only the affiliate code: no visitor id, UTMs or personal data. Purpose: calculate and pay the commission owed to the affiliate (contract performance / legitimate interest). Without consent the code does not reach the track's visitor, Meta or GA4; it only goes to SimIntPay with the checkout and comes back in the sale event. The privacy policy lists it (cookie table, legal bases and the "before you choose" text). **Legal review of this legal basis is pending** before publishing. When this text goes live, bump the banner text version in the track panel together with the policy (they must match; the track agent records where that constant lives).
- **Sales of people who did not accept** are stored and counted in the panel (Faturamento, revenue), but are **not** sent to Meta or GA4. The panel labels them "Sem consentimento". Visitors from before the banner count as not accepted until they accept.
- **A refusal in the visit of the sign-up wins over any earlier acceptance.** The sign-up form sends the banner choice (`tracking.consent`: `granted` or `rejected`, read from `_trck_consent`). With `rejected`, the backend replaces the tracking saved by an earlier sign-up with the refusal alone (plus the affiliate code `aff`, which comes from the necessary cookie `_trck_aff` and is not marketing data) and relays it with the sale; the track then links the sale to no visitor (not by `src`, e-mail or a shared phone), stores it as approved without consent and makes zero attempts to Meta/GA4. Without a choice (banner unanswered or script blocked), the saved tracking is kept as before.
- **Faturamento shows "Banner recusado"** next to the sale status (table, mobile card and sale detail) only for that explicit refusal, read from the sale's `match` (`consent: "rejected"`). A sale whose buyer left the banner unanswered shows no such label; its Envio column stays "Sem consentimento (não enviada)". An erasure request clears `match`, so the label disappears from that anonymized sale.

## Panel analytics (track)

- **Periods and comparison** (panel time zone): the presets follow Meta Ads Manager. "Últimos N dias" are the N full days before today (they end yesterday, like Ads Manager, so the same filter shows the same spend in both places); "Hoje", "Esta semana" and "Este mês" include today. Comparison ("vs anterior"): "Este mês" compares with the same days of the previous month (1–8 Nov × 1–8 Oct; if the previous month is shorter, it stops at its last day); "Mês passado" compares with the whole month before it; every other preset and custom ranges compare with the same number of days right before; "Máximo" does not compare. A KPI shows "novo" only when the previous value was zero and the current one is not, and "sem comparação" when either side does not exist (e.g. conversion without visitors, average ticket without sales, which then shows "—").
- **Meta spend when the detail is cut:** the ad-level insights stop at 10 pages (5,000 ad × day rows). When Meta still had more rows, the track fetches the account totals (one small account-level call) and uses them for spend, ROAS, CPA and the daily chart in Campanhas and Visão geral; the campaign tree stays partial and the panel shows a warning. If even the account totals fail, the warning says the spend shown is below the real one.
- **Origin without UTM:** the visitor keeps the first external site they came from (`document.referrer` sent by `t.js` on identify). Referrers from the tracked sites themselves (authorized origins and their subdomains) and from the checkout domains are discarded, and only origin + path is stored (no query string or `#`, which can carry personal data). The panel shows it with a friendly label (Google, Facebook, Instagram, YouTube, X, TikTok, Bing, LinkedIn, WhatsApp, ChatGPT…; other sites by domain): in Eventos' "Origem" column and event detail ("· sem UTM"), and in the journey's "Veio de". The event's UTM always wins; with neither, the origin is "Direto / sem referência". Visão geral's "Origens dos visitantes" counts the period's unique users by origin: the most recent `utm_source` of their events in the period ("UTM · fonte"), otherwise the referrer label; the 7 largest groups are shown and the rest is "Outros", so the total equals the period's unique users. It is the first known external origin, not the origin of each visit.
- **Campaign status and budget (Campanhas):** each campaign, ad set and ad shows its Meta delivery status (Ativa, Pausada, Em análise, Reprovada, Com problema, Pagamento pendente, Arquivada; Concluída once its end date has passed, unless it was archived: archived wins and the campaign goes to the archived group) with icon and label, and its daily or lifetime budget (with what remains) at the level where it was set: the campaign when it uses campaign budget, otherwise each ad set. When Meta reports the ad account itself as disabled or closed (`account_status` 2, or 100/101), every campaign, ad set and ad of that account shows "Conta desativada" / "Conta encerrada" instead, because Meta keeps their own status as it was although nothing delivers (archived still wins). Active campaigns with no spend in the period are listed at the end with zero metrics and "sem entrega no período", and expand to their ad sets and ads (zero metrics, each with its status, archived ones left out), so a new ad's review result shows before it spends; paused, archived or finished campaigns without spend, and campaigns of a disabled account, are not listed. Campaigns with spend in the period that Meta reports as archived, or no longer lists at all (deleted), go into a collapsed "Arquivadas ou excluídas" group at the end, showing their summed numbers; their spend stays in every total. A campaign only counts as deleted when that ad account's list came back complete, so a missing or cut list never hides an active campaign. Status and budget come from one cached copy per ad account, refreshed at most hourly (and on "Atualizar agora") inside the same rate limit; they never change spend, ROAS or attribution. If Meta does not answer, the tree shows no status and the panel says so.
- **Visão geral:** "Gasto" is the Meta Ads spend of all active ad accounts, read through the same cache and rate limit as Campanhas (no extra Meta call when either tab already loaded the period). "ROAS" here is the overall ROAS: revenue of the period's new sales ÷ spend (renewals excluded), including new sales that did not come from ads; the campaign-attributed ROAS (UTM) stays in Campanhas. In "Máximo", users, events and revenue start at the track's first data, while "Gasto" covers the whole ad account since its first spend; the Gasto card says so ("Desde dd/mm/aaaa (primeiro gasto na Meta)").
- **Páginas:** conversion per page, where a page is the domain + path without query string (UTMs, `fbclid`) or trailing slash. A person counts on **every** page they viewed in the period, so a buyer who saw the VSL and the sign-up page counts on both and the rows do not add up to the total. Checkout = viewers who fired `InitiateCheckout` in the period; purchases = viewers' approved sales in the period, renewals excluded (same rules as Faturamento). The table pages through every page in steps of 100 (ordered by users); the KPI cards always cover all pages.
- **Affiliates (Faturamento, Visão geral, Páginas, Vídeos):** the "Afiliado" filter (`?afiliado=CODE`, several values allowed; options "Todos", "Sem afiliado" and each code with its name when known) applies in Faturamento, Visão geral, Páginas and Vídeos, and not in Campanhas (it is per Meta ad, and spend is not split by affiliate). Faturamento has an "Afiliado" column (filterable) and a "Por afiliado" card (sales, revenue, commission and net per code, ordered by revenue; revenue counts renewals, acquisition numbers only new sales). In Visão geral, Receita, Compras, Conversão and the funnel follow the filter; the overall ROAS keeps new-sale revenue ÷ spend and the spend is not filtered (the card warns when an affiliate filter is on). Origens dos visitantes gets "Afiliado · CODE". The visitor journey shows the affiliate in origin/attribution (first and last touch) and on each purchase. The sale's affiliate and commission come from SimIntPay's `affiliate` field and are fixed after approval, like the other sale fields; a reversed commission shows on the sale detail without rewriting revenue.
- **Eventos:** each row shows the visitor ID, which opens that visitor's journey directly. The event type filter accepts several types at once (`?tipo=PageView,Lead`; a link with one type still works) and applies when the menu closes.
- **Geo:** the countries chart shows the top 10 plus "Outros / desconhecido" and its table view lists every country. The cities list shows 20 at a time with "Ver mais", up to the 500 largest, and states the period's total number of cities.
- **Vídeos:** retention of the VSL video. The VSL reports each play's progress (`trck('video')`): furthest point reached, seconds really watched (skips and replays don't count), the end and the second the button unlocks. One row per play in `video_views`. Play rate = plays ÷ PageViews of the video's page, counting PageViews only from the video's first recorded play (before it, plays could not be measured, so older views would lower the rate); the ⓘ shows that start when it falls inside the period. How to read the tab and why it is calculated this way: [track/docs/aba-videos.md](../track/docs/aba-videos.md). This data stays in the panel: it never goes to Meta or GA4 and is not an event (`events_log`, the overview's "Eventos" KPI and the funnel are unchanged).
- **Visitor journey** (`/painel/visitante/<trck_user_id>`, opened from the Eventos visitor column and the event and purchase details): everything recorded about one visitor, with no period filter. Shows visitor data (e-mail; name and phone only from a sale event such as a generated PIX or a purchase, since sign-up stores them hashed), origin and attribution (first touch = oldest record with UTMs, last touch = the visitor's current UTMs, first page, referrer, Meta ad click from `_fbc`), each purchase with how it was linked and its campaign › ad set › ad from the UTMs, other visitors with the same e-mail or phone hash (other devices), and a chronological timeline of events, video plays and every sale event (PIX generated, approved, refunded…) with the UTMs, page, location, IP and device of each record. Shows the newest 200 records first, with "load earlier".
- **Bot visits are ignored** (no visitor, no event, nothing sent to Meta/GA4): Meta and Google crawler networks, cloud and hosting networks (AWS, Azure, Google Cloud, Alibaba, Tencent, Oracle, DigitalOcean, OVH, Hetzner…), browsers that declare themselves bots, plain Chrome below version 100 (Chrome auto-updates; manufacturer and in-app browsers that ship older engines are not affected) and browsers driven by automation (`navigator.webdriver`). iCloud Private Relay networks are never blocked. Configurações › Saúde counts the ignored visits by reason since the last restart. Note for local tests: Playwright sets `navigator.webdriver`, so pages it opens are ignored unless it runs with `--disable-blink-features=AutomationControlled`.
- **Test mode (team browsers, plan 0008):** opening any tracked page once with `?rw_teste=1` turns the browser into a test browser on both sites (`t.js` writes `_trck_teste` on `.rastrewin.com`, 365 days); `?rw_teste=0` or "Sair" on the purple bar at the bottom of the page turns it off and starts a new, normal visitor (the test visitor id and UTMs are forgotten on each site). While on, the Pixel and the gtag do not load and every capture carries `test: true`; the consent banner works as usual (nothing is recorded without acceptance). The track marks the visitor as test (`visitors.is_test`; only the panel unmarks) and sends nothing of it to Meta or GA4: its events and `AddPaymentInfo` are stored with the response `{"test": true}` ("Teste (sem envio)"), and its sales get no `Purchase` (Meta or GA4) and are skipped by the automatic retry. An Administrator can also mark or unmark any visitor in the journey ("Marcar como teste" / "Deixar de ser teste"); marking applies to the whole history in the reports, but what was already sent to Meta stays there. Reports: Visão geral, Campanhas, Páginas, Vídeos, Geo and Faturamento's totals leave test visitors' events, plays and sales out and say so ("N visitantes de teste ficaram fora destes números", linking to Eventos); Eventos shows them with a "TESTE" tag, the "Teste" send filter and a "Mostrar testes" switch; Faturamento lists a test sale with the tag, outside the totals. It changes nothing for normal visitors, so the privacy policy and banner version stay as they are.
- **System health** (Configurações › Saúde, and a banner on every panel page when something needs attention): database size (sum of all tables) and growth estimated from the last 7 days, with a warning above 5 GB; the daily cleanup (late after 36 h without running); the backend's sale relay queue (heartbeat every minute; warns when a sale waits more than 30 min, the backend gave up on one, or there is no heartbeat for 10 min; "Tentar de novo" requeues the given-up sales); new sales from the last 7 days that did not reach Meta or GA4 after the 5 automatic attempts.
- **Daily summary tables: deliberately not built.** The heaviest panel numbers are unique users, which cannot be added up day by day (one person on three days would count three times), so pre-aggregated daily rows would barely speed them up while adding a table, a nightly job and a second source for the same number. Revisit when Configurações › Saúde shows `events_log` near a few million rows or a panel page takes more than 2 s.
- **Daily cleanup (retention, LGPD):** after 14 days it empties the technical JSON payloads of events (what was sent to and received from Meta/GA4; the event detail then shows empty JSON tabs and Meta status "expirado"); after 90 days it erases IP and browser of events and visitors and the raw webhook body; after 13 months without activity it deletes the visitor (e-mail, hashes, Meta/Google ids); after 5 years it anonymizes the personal data of sales and deletes consent records. Event rows, URLs, UTMs, approximate location, video plays and the sales' value/date/status/product are kept, so KPIs, funnel, Páginas, Vídeos and campaigns/ROAS do not change. What does change: the journey and the sale → visitor link of visitors deleted after 13 months, and the customer e-mail of sales older than 5 years. Periods live in one constant (`RETENTION_DAYS` in `track/src/lib/maintenance/retention.ts`).

## Panel users and access levels (track)

- The track panel has two fixed levels. **Administrador** sees and does everything, including Configurações (with Saúde) and Usuários. **Colaborador** sees the analytics tabs, the visitor journey and event/sale details, and can refresh campaign data, but not Configurações, Usuários or the health banner.
- For a Colaborador, customer name, e-mail, phone and IP are masked on the server (`m***@gmail.com`, `(11) *****-**21`, `187.45.*.*`); the raw webhook body is hidden, personal identifiers in the Meta/GA4 payloads show as `oculto`, and the Faturamento search ignores e-mails. An Administrador always sees full data.
- Users are managed in the Usuários tab by an Administrador, who sets each password (no temporary password, no e-mail). Deactivating a user or resetting their password signs them out at once. Nobody can change their own level, deactivate or delete themselves, and the panel always keeps at least one active Administrador.
- Logins created before the levels existed became Administrador; new users default to Colaborador. Recovery when the only Administrador loses the password: `create-admin` inside the track container. Owner guide: [track/docs/usuarios.md](../track/docs/usuarios.md).
